Web Performance

What users perceive, measured

Loading

When do I see what I came for?

Stability

Does the page move while I use it?

Responsiveness

Does it react as soon as I touch something?

Each question has a metric, and each metric breaks down to show where the time goes

Core Web Vitals

Three metrics, three “good” thresholds

LCP

≤ 2.5 s

Largest Contentful Paint: when the largest element is painted

CLS

≤ 0.1

Cumulative Layout Shift: how much the content shifts

INP

≤ 200 ms

Interaction to Next Paint: how long it takes to respond to an interaction

The thresholds WebPerf Snippets returns with each measurement, Google’s for the 75th percentile

LCP

LCP breaks down into four phases

TTFB
Load delay
Load time
Render delay
  • TTFB: until the first byte of the HTML arrives
  • Load delay: until the browser starts requesting the LCP resource
  • Load time: how long it takes to download
  • Render delay: from when it arrives until it is painted

CLS

Not every shift counts

They count

The ones the user did not cause: a banner that comes in without reserved space, a font that changes size when it loads

They do not count

The ones right after an interaction, like a panel that opens on a click

To fix it, the number is not enough: you need to know which nodes move

INP y LoAF

An interaction has three phases

Input delay

The main thread is busy and the event waits

Processing

The event handlers run

Presentation delay

Until the browser paints the next frame

Long Animation Frames (LoAF): name the script that blocks and what invokes it. A trace of the click names the function

Step 5

The gate in the CI of every pull request

for branch in pr-lcp-hero-lazy pr-cls-promo-banner pr-loaf-cart-handler pr-noop-refactor; do
  CANDIDATE=$branch docker compose run --rm -e OUT=/out/ci/$branch ci
  echo "$branch: exit $?"
done

Three failures and one pass. Read the report.md of each branch: the verdict, the explanation and what backs it
